How to interpret the timestamps and counts

The horizontal axis uses capture-file timestamps. Zero is session capture start when a manifest is available, otherwise the first decoded event. Step lines change only at recorded times; pixel positions are approximate. The table preserves full timestamp digits exported by TShark. Purple × marks are captured gateway ARP arrivals.

A message spanning TCP segments is assigned the capture time of the frame where TShark displays its completed reassembly. Multiple BGP messages in one frame, and multiple NLRIs in one message, can share a timestamp. Equal timestamps do not establish an order across different BGP sessions or capture points.

NLRI mode counts MAC-only and MAC/IP separately, including propagation and re-advertisements. Message mode counts distinct capture-point/frame/message identifiers that contain matching Type-2 records. An UPDATE containing both advertisements and withdrawals contributes once to each series; the series must not be added to obtain a unique-message total.

Filters and the time window apply before counting. Counts start at zero for the selected window. Experiment markers use the manifest's host-clock times. Packet observation time does not establish forwarding-table installation time, per-robot outage, or internal router processing time. Clock accuracy, capture loss, and TCP reassembly affect interpretation; digit precision is not an accuracy guarantee.
